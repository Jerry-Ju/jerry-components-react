# 修复 Bug

根据 Bug 描述，结合项目编码规范定位根因，输出最小改动的修复方案。**禁止直接修改代码。**

## 用户输入

从命令后的描述中提取（缺失则追问）：

- **Bug 现象**（实际表现、截图、报错信息）
- **预期行为**（应该怎样）
- **复现步骤**（如何触发）
- **影响范围**（组件 / 文件 / 场景，可选）
- **相关代码**（文件路径、行号、`@` 引用，可选）

## 必读规范

分析时对照：

- `.cursor/rules/component.mdc`
- `.cursor/rules/ts.mdc`
- `.cursor/rules/less.mdc`
- `.cursor/rules/dumi-doc.mdc`
- `.cursor/rules/git.mdc`

## 分析流程

1. 阅读 Bug 描述，明确现象与预期
2. 定位相关源码（组件、样式、类型、demo）
3. 追踪数据流 / 样式计算 / 渲染逻辑，找到根因
4. 排除无关因素，确认是否为最小修复点
5. 设计最小 diff，避免过度重构

## 输出格式（仅输出以下内容）

### 1. 问题引发原因

用 1–3 段说明：

- **根因**：为什么 Bug 会发生（代码 / 样式 / 逻辑层面）
- **触发条件**：在什么情况下复现
- **影响**：哪些场景受影响

### 2. 代码 Diff 方案

按文件列出最小改动，使用 unified diff 格式：

```diff
--- a/src/components/Example/index.less
+++ b/src/components/Example/index.less
@@ -10,7 +10,7 @@
-  width: 25%;
+  flex: 1;
```

每个改动文件需附一行说明：**改什么、为什么、影响范围**。

### 3. 验证方式

列出修复后如何验证（无需执行，仅描述）：

- 手动验证步骤
- 是否需要跑 `pnpm lint` / `pnpm dev`

### 4. 自检清单

- [ ] 改动范围最小，未引入无关修改
- [ ] 符合 `.cursor/rules` 编码规范
- [ ] 未使用 `any`、全局样式等禁止项
- [ ] 未破坏现有 API 或向后兼容

末尾固定询问：**「确认后应用修复」**

## 禁止事项

- **不得** Create / Write / Edit / Delete 任何文件
- **不得** 运行会修改代码或配置的命令
- **不得** 跳过根因分析直接给修复代码
- **不得** 扩大改动范围（重构、格式化、顺手优化）
- **不得** 在用户确认前应用任何修复

## 确认后（可选第二阶段）

用户明确回复「确认」后，方可：

1. 按 Diff 方案做最小改动
2. 运行 `pnpm lint` 验证
3. 简要说明修复结果与验证方式

未确认前，始终停留在分析与方案输出阶段。
